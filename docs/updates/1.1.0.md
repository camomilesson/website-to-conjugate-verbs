## 1. Instant answer feedback

Status: planned.

Load all verb data required for the practice session before the first question.
Check answers locally and display feedback immediately in both guest and
signed-in practice.

Signed-in practice currently waits for the server acknowledgement before showing
feedback, so preloading alone will not resolve the delay. Separate immediate
feedback from durable answer saving while preserving server validation,
idempotent retries, answer ordering, account isolation, and atomic completion of
history and counters. Define the pending-save, retry, navigation and final-result
behaviour before changing the flow; never imply that unsaved progress is saved.
Keep this scoped to the active session, without introducing offline persistence.

Verification: throttle network requests and confirm feedback appears without
waiting for a save; exercise failed saves, retries, rapid advancement, final-answer
completion and account changes without lost or duplicated answers. Check initial
loading/error/retry states in typing and choice modes.

## 5. Explicit choice for persistent sign-in

Status: planned.

Keep Google OAuth and add an unchecked “Keep me signed in on this device” option
at sign-in, with a short explanation that it saves the sign-in in this browser
between visits and that signing out removes it.

- Without opt-in, keep authentication in session-only browser storage.
- With opt-in, retain authentication across visits.
- Keep account identity, preferences and learning progress in Supabase either way.
- Verify the actual session/refresh lifetime and describe retention and withdrawal
  accurately in Privacy.
- Handle existing persistent sessions explicitly when introducing this choice;
  do not treat an existing token as proof of consent.
- Ensure OAuth redirects/PKCE, token refresh, multiple tabs, sign-out and account
  deletion work with the chosen storage strategy. Document that session storage
  is tab-scoped and test browser session-restoration behaviour rather than
  promising unconditional logout on browser close.

Use targeted consent at sign-in for persistent authentication. A general cookie
banner is not part of this change solely for that purpose; this does not classify
all other storage or third-party behaviour as exempt.

Basis: [AEPD cookie guide, p. 10](https://www.aepd.es/guias/guia-cookies.pdf)
distinguishes session authentication, and [European guidance, section 3.2](https://ec.europa.eu/justice/article-29/documentation/opinion-recommendation/files/2012/wp194_en.pdf)
describes an explanatory remember-me checkbox for persistent-login consent.

Verification: test both options through Google redirect and return visits, token
refresh, sign-out and existing-session migration. Confirm the same account and
progress return after a fresh sign-in. Update auth and operations documentation.

## 6. Targeted verb selection modes

Status: planned.

Add two practice selection modes using stored aggregate progress, without requiring
individual mistake history:

- **Least practiced:** prioritise verbs with the most unattempted verb–tense
  combinations, then the fewest total attempts. Zero means zero attempts, including
  absent records; attempted cells with 0% accuracy are not unpractised. Prefer
  unattempted combinations when generating questions from the selected verbs.
- **Most mistakes:** prioritise verbs with the lowest weighted accuracy
  (total correct / total answered), excluding unattempted verbs. Break accuracy
  ties using more attempts. Explain the ranking with “Lowest accuracy first.”

Select up to 20 eligible verbs, respecting the selected tenses and answer mode.
Use alphabetical order as a deterministic final ranking tie-breaker; keep normal
session question randomisation. Reuse existing question eligibility, person,
length and accent rules. Make insufficient-data and guest states clear; never
represent missing progress as mistakes. Keep manual verb selection available.

Verification: check absent records versus attempted 0%, weighted accuracy,
ranking ties, fewer than 20 eligible verbs, mode/tense filtering, empty accounts
and the generated question pool. Ensure these selections use current progress
and do not overwrite manual selections unexpectedly.

## 8. Personal account greeting

Status: completed.

The main Practice setup greets signed-in users with their first name, taking
Google given_name, full_name or name metadata in that order. Missing names show
“Welcome back.” Guest copy is unchanged. Names render as text and wrap when long;
the greeting does not appear in customization, active questions or results.

Verification: TypeScript and lint pass; guest setup was reviewed in-browser.
Signed-in named/unnamed and account-switch visual checks remain a hosted review
checkpoint; no live account was used for this batch.
