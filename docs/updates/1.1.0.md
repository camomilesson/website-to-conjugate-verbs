# Conjugadora 1.1.0

Status: implemented; final staging review pending. The package version remains unchanged until release.

This document records implemented changes and their verification. Hosted review
checkpoints are noted where they remain; final approval turns these into the
release notes.

## 1. Instant answer feedback

Status: completed; owner verified hosted staging practice.

All verb data needed for a session is loaded before the first question in both
practice modes. Existing preloading already supplied accepted answers and choice
options; the remaining delay was the signed-in save acknowledgement.

Answers now show locally checked feedback immediately. Signed-in submissions save
through a serial memory-only queue using the existing immutable submission IDs and
payloads. Questions can advance while saves are pending. A failed save pauses
manual/automatic advancement and answer entry, keeps feedback/drafts, and focuses
Retry save. Progression resumes only when retry is acknowledged. Unsent requests
stop when the session unmounts or its account changes; an already-sent request may
still commit. No offline queue or resume mechanism was added.

After the last answer, scores/mistakes can appear as “Practice answered” while
saves finish. Saved/completed wording and Repeat/New practice become available
only after all acknowledgements. Navigation/reload warnings remain active while
answers are pending, including on the results screen. Leaving explicitly warns
that unsent answers can be lost. Existing server ordering, idempotency, account
isolation and atomic final-answer/history/counter writes are unchanged.

Verification: queue regression tests cover feedback before acknowledgement,
serial draining, lost committed replies with identical retry payloads, pending
completion, pause during retry, effect resubscription and late requests after
unmount. Local browser review with synthetic auth and all real SQL migrations
covered typing under 20-second response delays, immediate feedback and advancement,
unsaved results/navigation warnings, choice feedback, a lost final committed reply,
retry and acknowledged completion. Four answers produced exactly four receipts,
four counted attempts and two history entries after retry. No live learning data
was used. No SQL migration or Edge Function deployment is required.

## 5. Explicit choice for persistent sign-in

Status: completed; owner verified hosted staging sign-in.

Settings now offers an unchecked “Keep me signed in on this device” checkbox with
an explanation of browser storage and the fact that account/progress remain saved
regardless of the choice. Without opt-in, authentication uses tab-scoped session
storage; with opt-in, it uses persistent local storage. The PKCE verifier uses the
same selected storage as the resulting session.

Sign-in first reloads Settings to initialize the Supabase client with the selected
storage, then consumes a one-use redirect flag and starts OAuth. Session-only tabs
use distinct SDK storage/broadcast keys so another tab's sign-in cannot silently
upgrade them. Reload preserves the current tab's choice. Blocked storage is
reported instead of silently changing persistence.

Existing unmarked persistent sessions keep working during the small tester
transition; they are not marked as consent. Testers should sign out and sign in
once to choose explicitly. No database migration, provider configuration change
or Edge Function deployment is required. Google redirects remain `/settings`.

Privacy explains session restoration/duplicated-tab caveats, refresh-token renewal,
sign-out/site-data removal and provider expiry/revocation. There is no new fixed
login-duration promise or general cookie banner. Supabase dashboard session limits
were not changed or inspected; actual provider limits remain a hosted checkpoint.

Verification: five new tests cover tab isolation, reload, existing sessions,
one-use redirect intent, blocked storage, and real SDK PKCE exchange/refresh/
sign-out with synthetic responses for both choices. Browser verification against
local synthetic auth covered both redirects, restored account preferences, reload,
separate-tab isolation, persistent sign-in in a new tab, and cross-tab persistent
sign-out. No live Google account was used in local checks. The owner subsequently confirmed
the hosted staging sign-in flows work before production promotion.

## 6. Targeted verb selection modes

Status: completed locally; hosted staging review pending.

Customize offers Least practiced and Most mistakes only to signed-in accounts.
Guests continue to see All, Common and Select. Progress loads when customization
opens, with loading/error/retry states. Ranking follows selected tenses, eligible
persons, answer mode and typing accent policy; stored counts combine all persons.

- Least practiced chooses up to 20 verbs with the most unattempted verb–tense
  combinations, then the fewest attempts. Missing records and zero-attempt cells
  are unattempted; attempted 0% cells are not. Questions prioritise unattempted
  combinations, then fill from the remaining eligible pool without duplicates.
- Most mistakes chooses up to 20 attempted verbs by lowest weighted accuracy
  (total correct / total answered), then more attempts. Unattempted verbs are
  excluded. The explanation says “Lowest accuracy first.”
- Spanish alphabetical order breaks remaining ties. Accuracy uses full precision.
  Normal length caps, person eligibility and choice distractor rules still apply.
- An empty account can use Least practiced; Most mistakes explains the missing
  attempts and disables Start rather than falling back silently.
- Both options are normal saved verb modes, alongside All, Common and Select.
  Starting a practice saves the mode; signed-in Settings can save it explicitly.
  The Practice home summary displays the mode name. Both quick-start cards and
  Repeat reload current progress and recalculate the verbs for their answer mode;
  they never reuse the previous resolved list as the selection rule.
- Switching modes replaces the verb selection like other presets. Back still
  discards customization drafts. Guest controls remain unchanged.

Verification: ranking/sampling tests cover zero attempts versus 0%, weighted
accuracy, full-precision ties, filters, obsolete IDs, empty accounts, the cap and
prioritised unique questions. Additional tests cover preference round trips,
restoring rules independently of cached IDs, new-run recalculation, quick-start
answer modes, home summaries and History labels. Local browser checks with
synthetic auth confirmed saving Most mistakes in Settings, persistence after
reload, a choice quick start using choice-specific counts, completion/Repeat, and
Least practiced persisting after a successful customized start.

Deployment: apply [202611090001_targeted_verb_modes.sql](../../supabase/migrations/202611090001_targeted_verb_modes.sql)
once after the previous four migrations, before using these modes on staging.
It extends the private practice-start validator and keeps existing data, public
owner/generation guards and grants unchanged. The local SQL harness passes all
five migrations and suites, including new-mode completion/History and invalid-mode
rejection. No Edge Function deployment or data rewrite is needed.
